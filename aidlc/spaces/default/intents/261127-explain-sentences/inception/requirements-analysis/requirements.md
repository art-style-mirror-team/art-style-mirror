# Requirements — #22 해석 문장 템플릿

## 의도 분석

- 이슈: #22 "해석 문장 템플릿 (입력 유형별, 등급별 문구, CLIP 키워드)"이고 담당은 D(김현승)다. 완료 기준은 "입력 3종 × 등급 3종 모두 자연스러운 문장"이다(`docs/plan.md` 8장).
- 목표: 결과 카드의 해석 문장이 입력 유형(사진·그림·스케치)과 신뢰 등급(높음·보통·낮음)에 맞게 바뀌게 한다. 실제 계산에 쓰지 않은 정보(흑백일 때의 색)는 말하지 않는다. CLIP 키워드는 점수 목록 대신 읽히는 문장으로 보여준다.
- 유형: 기존 기능 개선. 범위는 단일 구성요소(`modules/explain.py`의 `render_card()`와 문구 상수)이고 복잡도는 단순하다.
- 지금 상태(CodeKB `code-quality-assessment.md` "D 영역 — #22 관점"):
  - 입력 유형은 제목 한 줄에만 쓰인다.
  - 등급 문구는 두 갈래이고, "높음" 문구는 빈 문자열이다.
  - 스케치에도 "색감·선은 …"이라고 쓴다.
  - 키워드는 `키워드(0.71)` 형태로 나열만 한다.
  - 조사는 `이(가)`로 적는다.

## 기능 요구사항

### FR1 입력 유형 × 등급 9칸 문구표 [Q3]

- **FR1.1** `(input_type, level)` 조합 9개(`photo`·`painting`·`sketch` × `높음`·`보통`·`낮음`)마다 고유 문구를 담은 상수 표를 둔다. 9칸은 모두 비어 있지 않다. 각 칸에는 그 조합에 맞는 도입 또는 해설 문장이 들어간다.
  - 판정 기준: 9개 조합으로 만든 `result`마다 `render_card()` 문장이 그 칸의 문구를 포함하고, 서로 다른 9개 문장이 나온다.
- **FR1.2** "높음" 등급에도 해설 문구가 있다. 지금의 빈 문자열을 없앤다.
- **FR1.3** "낮음" 등급은 지금처럼 Top 3 대신 CLIP·OpenCV 두 관점의 결과를 따로 보여준다. 문구만 입력 유형에 맞게 바꾼다.
- **FR1.4** 계약 밖의 `input_type`이나 `level`이 와도 예외를 내지 않고 정해진 기본 문구를 쓴다. 지금은 `TYPE_INTRO`는 기본값을 쓰고 `LEVEL_NOTE`는 `KeyError`를 내는데, 이 처리를 하나로 맞춘다.
  - 판정 기준: `input_type="unknown"`이나 `level="?"`인 `result`에서도 `(str, Figure)`가 나온다.

### FR2 색 표현은 `gray` 기준 [Q1]

- **FR2.1** `result["gray"]`가 참이면 문장 어디에도 색을 말하는 표현("색감", "색·선" 등)이 나오지 않는다. 관점 엇갈림 문장은 선만 말한다(예: "분위기는 A, 선은 B 쪽에 가까워요").
  - 판정 기준: `gray=True`인 9개 조합 모두 엇갈림 문장에 "색"이라는 글자가 없다.
- **FR2.2** `gray`가 거짓이면 지금처럼 색과 선을 함께 말한다.
- **FR2.3** 제목과 도입 문구는 `gray`와 상관없이 `input_type`을 따른다. 예를 들어 `input_type="painting"`, `gray=True`이면 제목은 그림용이고 엇갈림 문장에는 색 표현이 없다.
- **FR2.4** "낮음" 등급에서 두 관점을 따로 보여주는 줄의 이름도 FR2.1을 따른다. `gray`이면 "선(OpenCV)"처럼 색을 빼고 적는다.

### FR3 CLIP 키워드를 문장으로 [Q2]

- **FR3.1** `result["keywords"]`의 키워드 이름을 이어 한 문장으로 보여주고, 점수는 카드 어디에도 보여주지 않는다. 키워드 순서는 받은 순서(점수 내림차순)를 그대로 쓴다.
  - 예: "두꺼운 붓 자국, 소용돌이치는 하늘, 선명한 원색이 두드러져요."
- **FR3.2** 키워드 목록이 비어 있으면 키워드 문장을 빼고, 예외를 내지 않는다.
- **FR3.3** 키워드 문장의 조사는 FR4로 마지막 키워드에 맞춘다.

### FR4 한국어 조사 도우미 [Q4]

- **FR4.1** 단어 끝 글자의 받침을 보고 조사를 고르는 도우미 함수를 둔다. 대상 조사는 이/가, 은/는, 과/와, 을/를이다.
  - 판정 기준: "밝기"→"밝기가", "선 방향 일관성"→"선 방향 일관성이", "정물"→"정물이", "부드러운 빛"→"부드러운 빛이".
- **FR4.2** 특징 이름(`FEATURE_KO` 값)과 키워드 뒤에 오는 조사는 모두 이 함수로 붙인다. 문장에 `이(가)` 같은 병기형이 남지 않는다.
- **FR4.3** 끝 글자가 한글이 아니면(영문 화가 이름, 숫자 등) 받침을 판단하지 않고 정해진 대체 규칙을 쓴다(가정 A2 참고). 화가 이름 바로 뒤에는 조사가 오지 않게 문장을 짠다(예: "**Vincent van Gogh** 평균에 더 가까워요").

### FR5 기존 카드 요소 유지

- **FR5.1** Top 3와 %, 신뢰 등급 표시, 닮은 화풍, 1·2위 대조(`compare()` 결과), 비슷한 명화, 상세 수치 줄(1·2위 차이·엔트로피·JSD·데이터셋 유사도), 면책 문구 `DISCLAIMER`는 지금처럼 카드에 남긴다.
- **FR5.2** 1·2위 대조 문장도 FR4 조사 규칙을 따른다.

## 비기능 요구사항

- **NFR1 계약 유지**: `render_card(result) -> (str, Figure)`의 이름·입출력과 `result` 키는 바꾸지 않는다. `contracts/interfaces.md`는 수정하지 않는다. 판정 기준: `tests/test_smoke.py`가 수정 없이 통과한다.
- **NFR2 테스트**: 9개 조합(입력 3 × 등급 3)과 `gray` 참/거짓, 빈 키워드, 계약 밖 값, 조사 도우미를 검사하는 동작 테스트를 `tests/test_explain.py`에 추가한다. 실제 모델을 쓰지 않는다(`result` dict를 직접 만든다). 판정 기준: `pytest` 전체가 통과한다.
- **NFR3 결정성**: 같은 `result`면 항상 같은 문장이 나온다(무작위 문구 선택 없음).
- **NFR4 코드 스타일**: `ruff format .`과 `ruff check .`이 통과한다.
- **NFR5 검토 용이성**: 9칸 문구표는 한 곳의 상수로 모아 PR에서 문구만 따로 읽고 고칠 수 있게 한다.

## 제약

- 수정 파일은 `modules/explain.py`와 `tests/test_explain.py`뿐이다. 다른 Unit의 `modules/` 파일과 `app.py`, `contracts/interfaces.md`는 건드리지 않는다(`AGENTS.md` 규칙 1·2).
- 이슈 하나 = 브랜치 하나(`feat/22-explain-sentences`) = PR 하나. 머지는 머지 커밋으로 하고, 커밋은 구현·테스트·기록으로 나눈다.
- `feat/37-ui-design` 브랜치도 `explain.py`의 `LEVEL_NOTE` 근처를 바꾸고 `build_view()`를 추가했다. #22가 먼저 머지되면 #37 쪽에서 `git merge origin/main`으로 충돌을 푼다. #22에서는 #37 코드를 가져오지 않는다.

## 가정

- **A1** [assumption] 키워드는 앞으로도 한국어 명사구다. 계약은 `(str, float)`만 정하므로, A의 #7 구현에서 영어 문구가 오면 FR4.3의 대체 규칙이 적용된다.
- **A2** [assumption] 끝 글자가 한글이 아닐 때의 대체 규칙은 받침 없는 형태(가·는·와·를)로 한다. 영문 이름은 대부분 모음 소리로 읽히거나 조사 없이 배치되므로 영향이 작다고 본다. 설계 단계에서 바꿀 수 있다.
- **A3** [assumption] `level`은 `assess_confidence()`가 돌려주는 세 값만 온다고 보되, FR1.4로 방어한다. 등급 경계값은 #24에서 정하며 이 작업과 상관없다.
