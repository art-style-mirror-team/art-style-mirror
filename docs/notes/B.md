## 다른 역할과 맞춘 결정

- **`direction` 특징은 방향 일관성(0~1)이다** (PR #44 리뷰, C·D 합의). 평균 각도(0~180)가 아니다. 선이 한 방향으로 모일수록 1, 흩어질수록 0이다. 키 이름과 float 형식은 그대로라 계약은 바뀌지 않았다.
- **최종 순위는 `fuse()` 결과만 쓴다** (`AGENTS.md` 규칙 8). 두 관점이 엇갈리면 숨기지 않고 함께 보여준다.

- **CLIP 모델은 A가 #5에서 정하고, `embed_text()`는 받은 문장을 그대로 임베딩한다** (PR #56 리뷰, 이슈 #5 댓글, 2026-11-26). B는 모델을 직접 불러오지 않는다. 모델이 바뀌면 `TYPE_PROMPTS`의 효과도 달라지므로 #8 평가는 #5의 모델로 다시 한다.

- **`intents.json`은 자기 PR에는 자기 intent 항목만 커밋한다** (D 결정, 2026-11-27, `docs/aidlc-guide.md` 4.3·6장). 공용 파일이지만 커밋한다. 다른 사람 항목이 바뀌어 있으면 `git add -p`로 빼고, 충돌하면 양쪽 항목을 모두 남긴다.
  - 머지된 PR #57의 항목(`261126-similar-works`)이 main 목록에 없다. `intents.json` 한 파일만 바꾸는 `chore: #13 AI-DLC intent 항목 추가` PR로 올린다. `uuid`·`request` 값은 B의 PC 파일에만 있다.
- **분할은 다시 하지 않고, 중복을 감안해 평가한다** (D 결정, 2026-11-27, 이슈 #3 댓글). B의 평가 코드는 A의 중복 목록을 읽어 "중복 포함/제외" 수치를 함께 낸다.
  - 이유: 검증셋 1,035장 중 26장(2.5%)만 학습셋 작품과 코사인 0.95 이상이고(0.99 이상 1장), #9 kNN에서 26장을 빼도 Top-1이 0.706 → 0.700(참고값, PR #59 리뷰)이었다. 다시 분할하면 `meta.csv`의 split이 바뀌어 진행 중인 #8·#9·#13과 C의 작품 기록을 다시 해야 한다.
  - 중복 목록: A가 학습셋과 코사인 0.95 이상인 검증셋 작품 id 목록을 A의 스크립트로 만들어 `artifacts/`에 둔다(파일 이름은 A가 정한다. 예: `near_duplicates.csv`, 열 `id`, `split`, `train_id`, `sim`). 계약 함수는 바꾸지 않는다. 0.95는 `similar_works()`의 `NEAR_DUPLICATE`와 같은 값이다.
  - 검증셋으로 낸 수치(#9~#15의 정확도·ECE, #27)는 "중복 포함"과 "중복 제외"를 둘 다 적는다.
  - #24 등급 경계는 중복을 뺀 검증셋으로 정한다. 중복은 `max_sim`이 0.95 이상으로 튀어 경계를 끌어올린다.

## 다른 역할의 변경 중 B에 영향을 주는 것

- **#14 `T_cv`와 #15 `w`는 C의 특징이 확정된 뒤에 정한다.** 둘 다 `features.predict_cv()` 결과로 계산하는데, C의 특징 정의(#17·#18)나 전처리(#16), 프로필(#19), 약한 특징 제외(#20)가 바뀌면 p_cv 분포가 달라져 다시 계산해야 한다. C의 #18~#20이 머지되기 전에는 계산 코드와 비교표 틀만 만든다. `T_clip`(#14)과 판정 방식 비교(#9~#12)는 C와 무관하므로 A의 임베딩이 나오면 바로 진행한다.
- **"스케치" 판정이 두 곳에서 따로 나온다.**
  - C의 `features.is_grayscale()`: 전처리 후 픽셀 색으로 판정한다. 결과(`gray`)는 특징 계산과 `predict_cv(gray=)`에 쓰인다. 흑백이면 선 특징만 쓴다.
  - B의 `detect_type()`(#8): CLIP으로 판정한다. 결과는 설명 문장 첫머리에만 쓰인다.
  - 거의 한 색으로 된 연한 그림은 `is_grayscale()`이 흑백, `detect_type()`이 `"painting"`으로 엇갈릴 수 있다(PR #42 리뷰). 2026-11-26 3차 리뷰에서, 이 경우는 픽셀만으로는 "색 조명 아래 스케치"와 구별할 수 없다고 정리했다. 그래서 `detect_type()` 결과가 #25의 판단 근거가 될 가능성이 크다. #8 평가 때 엇갈린 사례를 기록해 두면 #25 통합에서 처리 방법을 정한다. B가 이 엇갈림을 `fuse()`나 순위에서 따로 고치지는 않는다.
